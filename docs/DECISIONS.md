# Decisions log

Decisions made against the build spec (Section 13 and deviations), with date and reason.

| # | Date | Decision | Why |
|---|---|---|---|
| 1 | 2026-11-03 | **Postgres (Supabase) instead of Airtable for v1.** Accessed only through `src/lib/db/*` via Prisma. | Owner approved. Airtable has no row-level security, ~5 req/s limit, and a single whole-base token. Postgres gives transactions, unique constraints and parameterized queries (removes the formula-injection class entirely). |
| 2 | 2026-11-03 | **Current Next.js (16) with Pages Router**, not 14. | Owner approved. 14 is two majors behind and was affected by CVE-2025-29927 (middleware auth bypass). |
| 3 | 2026-11-03 | Production build uses webpack (`next build --webpack`). | Turbopack's Pages Router output injects an inline bootstrap script, which would force `'unsafe-inline'` in `script-src`. With webpack the CSP is `script-src 'self'` with no exceptions (verified in a browser). |
| 4 | 2026-11-03 | `style-src 'unsafe-inline'` remains. | React `style` props and next/font CSS need it. Inline styles cannot execute script; `script-src` stays strict. Documented per spec defect #14. |
| 5 | 2026-11-03 | Brand "Shepherd Staffing" and support@shepherdstaffing.com are **placeholders** (`src/lib/brand.ts`). | Owner to confirm legal entity name and support email before launch (spec §13 #2). |
| 6 | 2026-11-03 | Stripe Checkout/Portal are full-page redirects; no Stripe.js. | Removes all Stripe origins from the CSP. |
| 7 | 2026-11-03 | Passwords capped at 72 bytes. | bcrypt (spec-mandated) silently ignores bytes past 72; rejecting is safer than truncating. |
| 8 | 2026-11-03 | Signup with an existing email returns the normal "check your email" response and emails the account owner instead. | Stops the signup form being used to discover who has an account. |
| 9 | 2026-11-03 | `past_due` keeps paid access (with a banner) while Stripe retries the card; `cancelled` = expired. | Avoids locking out paying churches over a single failed charge. Change in `computeEntitlements` if you prefer immediate lockout. |
| 10 | 2026-11-03 | Client IP header configurable (`CLIENT_IP_HEADER`). Default `x-real-ip` (set by Vercel). | Once Cloudflare proxies the domain, set it to `cf-connecting-ip`, or per-IP rate limits would see Cloudflare's IPs. |
| 11 | 2026-11-03 | Breached-password check (HIBP k-anonymity) is on by default, fail-open; `HIBP_CHECK=false` disables. | Only 5 hex chars of a SHA-1 leave the server; outages never block signup. |
| 12 | 2026-11-11 | **PreQual AI combined into Shepherd Staffing as its screening engine; no second product, no second database.** PreQual's questionnaire + 0–100 rubric ported to `src/lib/scoring/prequal.ts` and a `PreQualAssessment` table; standalone PreQual brand retired, name kept only as a feature. | Generic job-search was rejected (Indeed ~20% / LinkedIn ~15% share, network effects, $0 budget) and PreQual-alone was rejected (screening is a feature — HireVue/Criteria/Checkr/ATS already do it). The winnable model is the non-mega-church niche, where PreQual as a free lead magnet grows Shepherd's candidate database. See `docs/PREQUAL_COMBINED_PLAN.md`. |
| 13 | 2026-11-12 | **M3 Profiles: `src/lib/profiles.ts` is the only sanctioned path to the encrypted profile columns.** API routes and pages decrypt on read / encrypt on write through it, and never return ciphertext. Profile score is completeness only (candidate 14 fields, church 15), 0–100, recomputed on every save — not a quality judgement. Public views strip all private fields; `familyNotes` is recruiter-only and is never sent to AI or other users. | The db layer's own comment already said encrypted columns are "written only through lib/profiles" — this makes that rule real before any profile page exists. Verification stays admin-only (M8); M3 shows verified status but does not grant it. |
| 14 | 2026-11-12 | **M4 Billing: the webhook is the only writer of subscription state.** Checkout creates a Stripe session and writes nothing to our DB; the webhook (signature-verified, event-id claimed once as the idempotency lock, claim released on failure so Stripe retries) syncs the subscription row and the user's status, then invalidates entitlements. Prices live in env ($49/mo, $299/yr), never in code. | A checkout can be abandoned or a payment can fail after the redirect, so granting access from the client redirect would give away memberships. Test-mode Stripe keys until launch; no live charge has been run from this code. |
| 15 | 2026-11-12 | **M5 Matching: the score is a deterministic rubric, the LLM writes only the narrative.** Score weights theology 30 / position 20 / experience 15 / geography 15 / PreQual 20; PreQual is optional-neutral (10/20) so unscreened candidates are not punished. Pairs are hash-cached and skipped when inputs have not changed; LLM narrative runs only for the top 5 pairs per refresh (score ≥ 55), the rest get rule-based text. Private/encrypted profile fields are never sent to the model, and every model call is logged to AiUsage. Chat trial cap is 10 messages *lifetime* (atomic increment), not a rate limit — a 429 would lie about it. | A black-box LLM score cannot be explained to a church or a candidate, cannot be cached, and fails when the key is missing. The rubric is explainable, testable without an API key, and cheap; the LLM adds the human-readable note where it is worth the cost. |
| 16 | 2026-11-12 | **M6 Messaging: contact is a request, not an open door.** A paid member contacts a match; the recipient accepts or declines. Only acceptance shares contact details and opens both-way writing. While a request is pending, nobody writes more — the request itself is the message. A declined thread can be re-requested; a block closes it. | Church hiring is a trust decision, and cold DMs to candidates (or to churches) are the fastest way to burn it. The request step gives both sides a dignified no, keeps contact details private until both sides opt in, and makes the inbox a short list of people who already said yes. |
| 17 | 2026-11-12 | **M7 Interview: churches see the evaluation, never the raw answers.** The candidate's written answers are encrypted and visible only to the candidate and the evaluating recruiter. A church sees the 0–100 rubric score, the per-question scores and notes, and the recruiter's note — only if the candidate shared the interview with them. Evaluation is a human 0–4-per-question rubric, not a model. | A candidate's own words about calling, conflict, and failure are the most sensitive thing in the product. Sharing them wholesale with every matched church would be a privacy failure and would make candidates write guarded, useless answers. The rubric keeps the signal (how the recruiter judged the answers) without handing over the raw text, and a human score is defensible in a hiring decision in a way a model score is not. |
